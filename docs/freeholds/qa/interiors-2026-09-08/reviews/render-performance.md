## Findings

1. **[SHOULD-FIX] High confidence: a stalled new zone dependency can indefinitely hold arrival and renderer shutdown.** `src/render/zone_character_dependencies.ts:25`, `prepareZoneCharacterDependencies`, awaits raw `Promise.all(prepareCharacterUrl)` with neither cancellation nor a deadline. `Renderer.prewarmZoneAt` awaits it before creating its 5000 ms deadline, and `arrival_warmup.ts` waits for `prewarmZoneAt` before revealing. `Renderer.shutdown` explicitly awaits every pending zone-prewarm promise. `assets/loader.ts::withRetry` retries only rejected loads and has no request timeout; a pending response need never reject. The new dependency list includes previously lazy/streamed models, so this adds an unbounded network barrier to previously bounded/fail-soft construction. The generation checks correctly reject a completion after shutdown, but cannot run until the dependency finishes. `tests/renderer_zone_dependency_lifecycle.test.ts` resolves its dependency promise after calling shutdown, so it does not prove shutdown without that completion. Smallest correction: give this dependency wait an owner cancellation signal and an existing bounded preparation deadline, let the shared asset fetch remain cache-owned if necessary, and retain the current no-build/no-publication generation guards. Add never-settles and shutdown-before-resolution tests, then resolve the old load and prove no late work. Do not make optional cosmetics required for settle.

2. **[SHOULD-FIX] High confidence: new temporary dressing instances have no terminal owner.** `src/render/freehold/interior_dressing.ts:93`, `buildFreeholdPrewarmGroup`, allocates fresh `THREE.InstancedMesh` objects and their instance matrices each time. `DungeonInteriors.buildPrewarmGroup` mounts them in `interiorPrewarmGroup`, but `Renderer.cleanupPrewarmArtifacts` only removes that root and later nulls it. The new objects are not passed to `OwnedInteriorResourceRegistry`, unlike live interior meshes. Installed `node_modules/three/src/renderers/webgl/WebGLObjects.js::onInstancedMeshDispose` owns release of per-instance attributes and binding states; removing a root does not call it. Keep the shared prepared geometry/materials alive, but explicitly dispose the temporary InstancedMesh objects once all compile/upload users have settled, including resume and retirement. Add a behavioral terminal-owner test proving disposal once and no shared geometry/material disposal. Native byte growth is not measured here; this finding is the missing explicit ownership arm, not an asserted measured leak rate.

3. **[SHOULD-FIX] High confidence: the new perf acceptance validator can pass contradictory raw event evidence.** `scripts/freehold_interior_route.mjs:317`, `freeholdInteriorPerfFailures`, requires finite begin/end counters but trusts `arrival.gpuDelta` without deriving or cross-checking it against `arrival.gpuBefore` and the final sample. A read-only Node probe copied the parent's fresh desktop samples, increased the Inn's raw `sampleEvidence.end.gpuCounts['live-program']` from 5 to 6, retained the derived delta 0, and the real exported validator returned `[]`. Missing entry baseline/entry timestamp also passes the current synthetic clean fixture. The existing live producer computes the delta correctly and the current recorded artifacts are internally consistent; this is an acceptance-integrity defect, not evidence that this capture was altered. Require finite monotonic entry and sample counts/timestamps, derive the final delta from raw entry-before and sample-end, and reject inconsistent stored delta/after fields. Pin a positive raw end counter with a stale zero derived delta as a failing case.

4. **[NOTE] High confidence: the perf tour's requested preset is not fully pinned before boot.** `scripts/perf_tour.mjs:501` writes `graphicsPreset` but omits `graphicsDefaultApplied`. `src/main.ts` explicitly calls `firstRunGraphicsPreset(settings.get('graphicsDefaultApplied'))` and can overwrite a recognized device's supplied preset. The screenshot harness correctly seeds both fields, but the perf runner does not. Both inspected actual tours report effective low, so this does not invalidate those four measured room windows. For reproducible later reruns, seed the marker as well and have this scenario retain/assert the effective setting/tier rather than merely trust `PERF_PRESET=low`.
