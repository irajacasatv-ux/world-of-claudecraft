## Scope and affected storage

The proposed eight ItemDefs and one Hearth page expand catalogs used by existing deserializers. That changes the permitted persisted membership even though it adds no field or schema. The finite immutable trial schedule is content data and, under the requested design, is not itself saved or used to recompute durable paid bills in this contribution.

At initial inspection the tracked diff comprised only NPC-bootstrap extraction and its barrel. The furnishing identity module was untracked and the complete ItemDefs, page and numeric rows had not landed. No DDL, runtime SQL, character shape, deed serializer or Reliquary serializer changes existed against the requested baseline. The later working-tree snapshot also included authoring scripts and tests being produced by other agents. This review does not admit their unfinished final contents.

Affected existing blob: `characters.state`, specifically `deedStats.itemsDiscovered` and `reliquary.firstFind` (including its folded `count`), `reliquary.recent`, and `reliquary.illuminatedPages`. Actual purchased copies ride the existing inventory, personal-bank and vendor-buyback fields. Existing guild-bank, mail and World Market custody can carry the new item IDs under the already-shipped furnishing custody contract; there is no proposed new storage table or write path. No additional deed IDs are proposed here, so no new direct `character_deeds` obligation is introduced by this slice.

The database review's predicted +632 raw maximal-fixture bytes is supplied planning evidence, not an independently measured result in this review. ## Verified compatibility behavior and release conditions

1. High operational severity, high confidence, established release condition: older catalog loaders permanently discard new cosmetic membership after a save. `src/sim/deeds.ts:505` accepts a discovered ID only when its local `ITEMS` owns it. `src/sim/reliquary.ts:194` drops uncatalogued first-find rows and therefore their counts; `src/sim/reliquary.ts:242` drops unknown illuminated-page IDs; `src/sim/reliquary.ts:301` drops uncatalogued recent IDs. The prior integration release has the same gates at `src/sim/deeds.ts:376` and `src/sim/reliquary.ts:185`, `:231`, and its narrow recent restore. The requested baseline has the same current predicates. This is verified code behavior, not a newly discovered serializer defect.

   The accepted repository policy is explicit in `DEPLOY.md:302`: content-ID additions require a fleet-wide-in-one-pass boundary; rollback across that boundary requires restoration from backup for the state that referenced new IDs. That policy already solves the release acceptance question. Keep the bounded allowlists; do not add generic unknown-ID preservation or a new persistence-version framework merely for these eight content records.

   A contribution-specific release note should name the eight furnishing IDs and `hearth_basics`, link this existing policy, and state that all character-writing processes must carry the compatible catalogs before trial-created or production-created state can reach them. Turning `freeholdsEnabled` off suppresses acquisition through the furnisher; it does not recover metadata already stripped by an old writer and is not a safe binary-rollback claim. Isolated development test saves do not authorize reopening production writers on older catalogs.

2. No verified new migration defect in the proposed scope. Existing populated characters lacking the new discoveries/page retain explicit empty defaults through `freshDeedStats` and `freshReliquaryState`. There is no renamed field to bridge, new column to backfill, new constraint to validate, seed race, query predicate/index, or migration-order change to review. Those checks are not applicable while this remains catalog-only.

3. High confidence, unchanged save-path coverage: `src/sim/sim.ts:3477` restores the deed and Reliquary fragments and `:4303` / `:4309` serializes them through their shared sparse helpers. `server/game.ts:4326` and `:4418` use that serializer for character writes; autosave runs through `saveAll` (`:2720`), leave through `saveCharacterOnLeave` (`:4152`), and shutdown through `server/main.ts:4205`.
