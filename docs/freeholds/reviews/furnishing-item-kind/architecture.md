## Findings requiring coverage follow-up

These are coverage findings, not claims that the inspected implementation currently misbehaves. The coordinator is editing the test file in parallel, so locations identify the review snapshot and the named tests/functions are the stable anchors.

1. **P2, high confidence: successful furnishing crafts are not yet pinned for draw count or same-seed replay.** `tests/furnishing_item_kind.test.ts:475` checks one rare signed output, but does not observe `rng.next`, exercise a Jack craft, or replay a command sequence twice. The existing `expectNoMutation` helper is valuable for refusals and cannot establish success-path draw count. Remediation: pin one draw for an ordinary successful furnishing craft and two for Jack, with no stat/Perfecting grant; replay a successful craft plus a storage round trip and a rejected command in two equal-seed worlds, comparing saved state, events, and RNG tail. A forced proc on a malformed Masterwrought furnishing should also keep its signed copy free of Perfecting/rolled power payloads.

2. **P2, high confidence: several new capability guards are only tested with data that the old fallback would already refuse.** `tests/furnishing_item_kind.test.ts:316`, `:323`, `:328`, `:383`, `:408`, `:422`, `:467`, `:510` use a slotless, use-less, non-Masterwrought definition. Removing the added explicit guard would leave those cases green. Remediation: reuse the existing synthetic fixture with forged slot/use/feast/masterwrought/stat fields for equipment/use, apply-enchant admission and resolution, Perfecting and its apex identity/view, crafting bonus/head start, and fishing. Assert literal denials plus unchanged inventory, currency, equipment, effects, and zero draws. The added malformed stack, gathering, charm, Perfecting-bonus, and heroic tests already address their respective arms.

3. **P2, high confidence: the changed vendor service branch has no actual purchase regression.** `tests/furnishing_item_kind.test.ts:750` checks vendorCountForced and buyPurchaseTotals, but never invokes buyItem. It therefore cannot catch the furnishing-to-riding-service delegation that was found and fixed during implementation, nor prove one free cell rejects a two-copy purchase. Remediation: stock the synthetic item through the existing test vendor seam, exercise an ordinary count purchase and the capacity boundary, and exercise a runtime-forged teachesRiding furnishing through buyItem, asserting ordinary item ownership, no riding grant, and the expected payment behavior. Also pin the existing soulbound/honor/service count restrictions.

4. **P2, high confidence: unbinding has no direct furnishing command/resolver regression.** `tests/furnishing_item_kind.test.ts:463` checks only the eligibility leaves. Remediation: give the player a synthetic furnishing copy with `boundTo: 0` and `bindOnTrade: true`, call `unbindItem(sim.ctx, ID, sim.playerId)` under `expectNoMutation`, and assert `{ok:false,itemId:ID,reason:'unbind_not_eligible',fee:10000}` for the current rare fixture. The shared resolver signature is `resolveUnbind(stations, meta, pos, itemId)` at `src/sim/professions/commission.ts:191`; the kind deny precedes range, binding and payment.

5. **P3, high confidence: the furnishing transport tests only sample the lock matrix.** `tests/furnishing_item_kind.test.ts:551` tests the shared predicate for furnishing and quest only; `:618` samples only one guild-bank bound-copy lock. No synthetic furnishing test currently drives soulbound/noMarketList/armed/bound refusal through each actual mail/market/guild-bank path, or proves the intentional personal-bank allowance and trade-party exception. The code inspection confirms the old predicates and ordering remain exact, and existing suites may provide further evidence, so this is a coverage nit rather than a found transfer vulnerability. Remediation: small table-driven synthetic tests for the relevant per-pipe lock distinctions, literal refusal ordering, and unchanged source/destination state; add all old kind literals and an unknown runtime value to the shared predicate's equivalence test.

6. **P3, high confidence: the stackSize field comment is now additionally stale.** `src/sim/types.ts:1112` still says the default is one for weapon/armor/bag/tool and twenty for everything else. Furnishings are guaranteed one even with an override, so that comment contradicts the new public type contract. Remediation: point the field documentation at stackSizeOf without repeating a partial kind roster, or state the furnishing exception explicitly. This was already incomplete for prior unstacked kinds and has no runtime effect.
